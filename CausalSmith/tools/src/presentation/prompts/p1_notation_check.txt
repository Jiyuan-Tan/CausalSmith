You are auditing the NOTATION-RESOLVABILITY of a paper's frozen formal layer — the
one check the equivalence gate cannot do (it verifies statements MATCH the Lean,
never that a reader can resolve their symbols). A self-contained paper must let a
reader resolve every named object a statement uses back to exactly one defining
statement.

ORDER IS NOT YOUR CONCERN. The environments are listed in paper order, but a
deterministic gate places definitions and assumptions before explicit consumers in the
graph and paper references; supporting results retain their planned homes. Matching
variable names do not establish object identity. You judge only
WHETHER some environment defines each symbol — anywhere in the layer, before or after
the use — and whether the uses agree with that definition. Never ask for anything to
be moved.

TASK. Find every NAMED operator, predicate, function class, law family, or rule
symbol that a STATEMENT body (theorem / lemma / assumption / definition) USES but
NO environment DEFINES. A symbol is defined iff some environment introduces it: its
title names it, or its body says "we say … when", "the class … is", "denote … by",
"let … be", "$X := …$", "define …", "put …", displays a defining equality, or lists it
as a component of a named structure ("a model is a tuple $(\pi, S, M)$ where $\pi$ is
the environment law"). Do not demand a second environment for notation defined
locally in the same anchored environment, and do not flag a later use merely because
it omits a cross-reference. If a missing reference makes the identity of a named object
ambiguous, report `wrong-ref` and request an exact reference to its defining environment.

Before reporting a problem, search the whole layer for the exact symbol stem and its
family-level definition. Do not flag locally bound variables, record fields,
coercions, standard construction syntax, ordinary notation used only on a
definition's right-hand side, or a decorated variant of a defined symbol whose
decoration the defining environment explains.

FLAG, per symbol, the worst applicable case:
- `undefined` — used in a statement but NO environment defines it (introduced only in
  passing, or never). E.g. a class `\mathcal H^\beta(…)` or an operator
  `\mathrm{overlapDen}` used in assumptions/lemmas with no defining environment.
- `rendering` — the name is an implementation alias, coercion, or bundling operation that
  should be translated into ordinary mathematical content in the using environment. Repair
  that environment; do not create a definition for implementation syntax.
- `wrong-ref` — the use carries a `\cref{obj:X}` but env X does NOT define the symbol
  (e.g. referencing the boundary-extrapolator definition for the Hölder class).
- `mismatch` — the defining environment and the use disagree on the symbol's
  parameters/arguments (defined as `\mathcal H^\beta(L;[0,t_0])` but used as
  `\mathcal H^\beta(C_\beta;[0,t_0])` with no statement that the constants coincide).

EXCLUDE standard mathematics no reader needs defined: `\mathbb R`, `\mathbb E`,
`\Pr`, `\mathbb 1`, `\vee`/`\wedge`/`\le`/`\to`, Greek parameters (κ, β, λ, …),
ordinary functions (e, μ, g), and the ambient covariate space `\mathcal X` IF the
setup/observable-law definition introduces it. Flag only genuinely NAMED objects a
reader of this paper could not resolve.

OUTPUT — return ONLY this JSON on stdout, nothing else:
{"clean": true|false,
 "problems": [{"symbol": "<as it appears, e.g. \\mathcal H^\\beta>",

"clean": true with an empty problems list iff every named symbol is resolvable.
